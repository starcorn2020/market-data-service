## 1. 題目理解與不變量切入

題目核心只有兩件事:**(a)** 把 `feed-sim` 噴出的 `BookMessage` 收下來,**(b)**
對外同時提供「取最新快照(req/resp)」與「即時推播(pub/sub)」兩種 API,而且
慢或斷的下游**不能**反壓到 ingest 或其他下游。一切設計都圍繞這條反壓邊界。

實作上把它具象成四條編譯期 / runtime 守得住的不變量(`AI_Guildline.md` §5):
**I1** ingest 永不阻塞、**I2** 訂閱者彼此隔離、**I3** `feed-sim` 只透過 `Upstream`
trait 接觸、**I4** 對外 API 不洩漏 `feed_sim::*` 型別。剩下的章節都是這四條
在具體模組上的落地。

`README.md` 明示 Non-goals(persistence / auth / TLS / multi-region /
L3 reconstruction);把這些當**禁區**而非「之後加」。例:`Service` 接 `feed-sim`
的入口只接觸 trait `Upstream`,讓未來換 iceoryx2 變成只動 `upstream/feed_sim.rs`
一個檔——這是 N1 對齊,而非 over-engineering。

## 2. 整體拓撲

```
                ┌──────────────────────────────┐
                │  FeedSubscriber  (feed-sim)  │  ←─ N1:transport 黑盒
                └──────────────┬───────────────┘
                               │ Upstream::receive  (I3 唯一接點)
                               ▼
                ┌──────────────────────────────┐
                │  ingest_loop  (std::thread)  │  ←─ I1 hot path
                │  put snapshot → publish bus  │     順序不可換
                └────────┬─────────────┬───────┘
                         │             │
                         ▼             ▼
                  ┌────────────┐  ┌──────────────────────┐
                  │ Snapshot   │  │ Bus                  │
                  │ DashMap    │  │ DashMap<Figi,        │
                  │ Figi→Book  │  │   broadcast::Sender> │
                  └─────┬──────┘  └──────────┬───────────┘
                        │ (R/R 拷貝回傳)       │ subscribe → 內部 fan-in 成 mpsc
                        ▼                    ▼
                  ┌─────────────────────────────────────────┐
                  │  tonic gRPC server (single wire)        │
                  │  - unary GetSnapshot                    │
                  │  - server-streaming Subscribe + I2 隔離 │
                  └─────────────────────────────────────────┘
```

ingest 是**唯一一條 std::thread**,獨佔 `FeedSubscriber`(`!Sync`,編譯期保證);
tonic 跑在 tokio runtime。橋樑是「snapshot put + bus publish 都不阻塞」的純記憶體
操作,加上 bus 內部的 `broadcast::Sender::send` 在無 receiver 時 noop、有 receiver
時寫 ring buffer 滿了直接覆蓋舊資料。換句話說 **ingest 在 hot path 上不會 .await、
不會持鎖跨 yield**,這正是 I1 的編譯期 + runtime 雙重守護。

## 3. 八條已落地的設計決策

> 對應 `AI_Guildline.md` §14.1。每條一段,先講做了什麼、再講為何不選另一條
> 看似等價的路。Pass-3 / Pass-5 的 §6.5 D1 / D2 在這裡用敘事方式重述。

### 3.1 `Arc<DashMap<Figi, BookMessage>>` 做 snapshot 表

寫端(ingest)每秒上千筆覆寫,讀端(`GetSnapshot` RPC)每秒個位數。`DashMap`
把表切成多個 shard,每個 shard 自己一把 RwLock;在「ingest 寫 FIGI-A、RPC 讀
FIGI-B」這種高機率不同 shard 的情境下,讀寫完全並行。對照組 `Arc<RwLock<HashMap>>`
則會把所有讀寫**串行化在同一把鎖**,ingest 越忙 RPC 越慢——直接違反 I1 在讀路徑
的延伸要求。`Arc` 本身**不是鎖**,只是引用計數,hot path 上 `Arc::deref` 是
零成本指標解引用;`clone` 才會付一次 atomic fetch_add,但 ingest loop 不 clone。

### 3.2 Per-FIGI broadcast channel 做 fan-out

`Bus` 內部是 `DashMap<Figi, broadcast::Sender<BookMessage>>`。訂閱一組 FIGI 時,
為每個 FIGI 拿到 `broadcast::Receiver`,再用一個 tokio task 把 N 條 receiver
合流(fan-in)成單條 `mpsc::Receiver` 給訂閱者。對照組「單一全局 broadcast +
訂閱者本地過濾」在訂閱者多但 FIGI 集中時更省記憶體,但慢消費者隔離要靠每個
subscriber 自己的 buffer 才成立,實作複雜度反而高;而且訂閱者只關心 3 個 FIGI
卻要 deserialize 全部 1000 個 FIGI 的 traffic,CPU 浪費明顯。Per-FIGI 的代價是
「subscribers 0 → 1 / 1 → 0 時要動 DashMap entry」,但這只在訂閱建立 / 關閉時發生,
不在 hot path。

### 3.3 滿了走 drop + `dropped_total` 累計

兩層緩衝(broadcast ring + 每訂閱者 mpsc)滿時都**累計到同一個
`Arc<AtomicU64>`**,不踢訂閱者、不斷流、不報錯。理由:gRPC stream 的 client
重連成本不低(要重新跑 `GetSnapshot` 對齊),drop 個別訊息對 market data 場景
通常比強制重連更輕量。Wire schema(`BookUpdate.dropped_total`)直接帶累積值
讓 client 做差分判斷自己漏了多少——比 per-message delta 強在「不依賴有序傳遞」
(任一筆收到即可對齊)。

### 3.4 gRPC (tonic) 作為唯一 wire protocol

`unary` + `server-streaming` 正好對應題目兩個 API,`.proto` 檔本身就是寫死的
設計文件;HTTP/2 / TCP 同時 serve 本機與跨主機(README §5)免費附送,不需要
另寫 length-prefixed framing。代價是 reviewer 環境需要 `protoc`,但用
`protoc-bin-vendored` 從 `build.rs` 注入 `PROTOC` env var,reviewer 不需手動裝。
**唯一的工程陷阱**是 tonic server-streaming 預設會把 backpressure 傳回 producer
——必須在 handler 內額外加一層 bounded `mpsc::channel` + `try_send`,絕不
`tx.send().await`,否則 wire 層慢消費者會反壓到 fan-in task 進而拖到 broadcast,
最終影響 ingest。這個陷阱在 `grpc.rs::subscribe` 用 `tokio::select!` 雙臂
(`sub.next()` + `out_tx.closed()`)的 cancel-safe 模式守住,並用註釋固化退出
語義。

### 3.5 Snapshot RPC 回 `oneof { Found, NotYet }`

README §3 明示「a clearly-defined no-data-yet signal」。protobuf `oneof` 比
「`Found` + bool empty 欄位」表達力強,client 端 pattern match 一定要寫到
`NotYet` 分支,編譯期就避免「忘了處理空資料」的常見錯誤。

### 3.6 Ingest 用 `std::thread`,不用 `tokio::task`

`FeedSubscriber` 是同步阻塞 API + busy-poll 風格(`wait` 阻塞固定 duration),
丟進 `tokio::task::spawn` 會吃掉整個 tokio worker(預設 worker 數 = CPU 核心數,
被吃一個影響顯著)。`std::thread::spawn` + `tokio::sync::mpsc` 把資料丟給
async 端是慣用做法,代價是 ingest thread 的生命週期要自己管(用 `IngestHandle`
封裝 `stop_token: Arc<AtomicBool>` + `JoinHandle`,加上 `Drop` 兜底 stop+join
防 leak)。

### 3.7 `FeedSubscriber` 包在私有 `upstream` 模組(I4 + D3)

`upstream/feed_sim.rs` 是整個 crate **唯一** `use feed_sim::*` 的檔案。對外
透過 `trait Upstream`(只 require `Send`,**不** require `Sync`,契合「整個
service 只能有一個 ingest 點」)接觸。立刻抽 trait + 用泛型靜態分派而非
`Box<dyn Upstream>`,讓:① 換 iceoryx2 時只動一個檔,client / wire schema 0 改動;
② 整合測試能注入 `MockUpstream` 做 deterministic 測試,不用真的跑 feed-sim
背景執行緒。**這條決策的 ROI 在 Phase 3 整合測試套件成型時得到實證**——所有
gRPC 邊界測試都跑在 mock 上,確定性 100%。

### 3.8 dependency:`anyhow` 下線 → `BoxError = Box<dyn Error + Send + Sync>`

最初規畫用 `anyhow`,後來盤點發現本 crate 只在三處(`Service::new` /
`Service::run` / `client.rs`)需要把多種錯誤匯流到一個 type;`BoxError` 已經夠用,
還少一個依賴。對外 `Service` API 用 `Result<T, BoxError>`,內部模組各自用具體
error 型別,匯流邊界自動 `From` 上轉。**reasoning**:三天 deliverable 不值得
帶不必要的依賴,且 `anyhow::Error` 的 `.context()` 在這個規模下沒有顯著價值。

## 5. 行為變化注意點

> 從 `Dev_Process.md` §6.7 行為變化清單搬,reviewer 拿 wire 跑 client 時可能
> 直接撞上的點。

### 5.1 過長 FIGI(> 12 bytes)→ 顯式 `InvalidArgument`

`marketdata-types::Figi::from_str` 是 `Infallible`,過長輸入會**靜默截斷**到
12 byte 前綴(其自帶測試 `figi_truncates_long_input` 驗證了這一行為)。如果
wire 層不做長度校驗,client 送 `BBG00ABCDEF1XTRA` 會被切成 `BBG00ABCDEF1` 去
snapshot 表查,大概率回 `NotYet`——但 client 不知道為何「明明送的是有效 FIGI
卻拿不到資料」。在 `grpc.rs` 兩個 handler 入口顯式 `if figi.len() > 12 →
InvalidArgument("figi too long (N bytes, max 12)")`,把這個 silent-correctness-trap
浮到 wire 邊界。

### 5.2 wire-pump task `tokio::select!` 雙臂(非 `while let`)

`grpc.rs::subscribe` 內部 task 用 `tokio::select! { sub.next() / out_tx.closed() }`
而非 `while let Some(book) = sub.next().await`。理由:client 主動斷線 + 該 FIGI
靜止時,`while let` 會卡在 `sub.next().await` 直到下一筆 publish 才走
`try_send::Closed` 退出——短時間 task 洩漏窗口。`select!` 副臂在 client 斷線
**立刻**喚醒退出,無洩漏窗口。兩條副臂都是 cancel-safe(tokio 文件明示),
本 select! 單次 iteration 內無 starvation 風險。

### 5.3 訂閱前 publish 的訊息不補發(from-now 語義)

`Bus::publish` 走 `senders.get(&figi)` get-only 路徑,無訂閱者時 noop(I1 核心)。
訂閱者建立後才接 ring buffer 的下一筆——這是 broadcast channel 的天然語意,
固化在 `messages_before_subscribe_are_not_replayed` 測試。Client 標準用法是
先 `GetSnapshot(figi)` 拿最新值對齊,再 `Subscribe(...)` 接增量,兩個 API 配合
讓 from-now 不成為缺陷。

## 7. Future work

> 與 `README.md` Non-goals 對齊:**知道有價值、知道怎麼做、刻意不做**。

### 7.1 真實 iceoryx2 替換 `feed-sim`(N1 對齊,trait 已鋪路)

當前 ingest hot path 在 1k msg/s 預設速率下 < 0.1% CPU,但 `feed-sim` 是 mpsc-based
opaque transport,μs floor 是物理下限。替換成 iceoryx2 共享記憶體後可降到 ns 級。
`Upstream` trait 是為此鋪的路:只動 `upstream/feed_sim.rs` 一個檔,
`Service::new_with_upstream<U>` 簽名不變,client / wire schema 零改動——這是
D3「立刻抽 trait + 泛型靜態分派」決策的真實 ROI。

### 7.2 Production graceful shutdown(`Service::run` L8 重構)

目前 `Service::run` 的 `tokio::select!` 三路合流在「ingest EOF」分支(path 3)
直接 return,不等 serve graceful 退出。production 嚴格場景應加 shared shutdown
channel:`shutdown_tx` 由 ctrl-c **和** ingest EOF 任一觸發,serve 走 graceful
drain。改造需要 `tokio::pin!(ingest_join)` + select! 用 `&mut`,複雜度 +30 行。
demo / 測試場景下當前行為 OK,reviewer 不會在 EOF 後立刻看 client 行為。

### 7.3 跨主機自動化測試

當前 README §5 的「同主機 + 跨主機」只由 `client.rs` 文件 doc 給手動指令驗證。
production 改造方向:docker compose 兩個 service,SSH tunnel,或直接 GitHub
Actions runner matrix。本次刻意不做(三天 deliverable 邊界外)。

### 7.4 對齊 Non-goals 的明確不做項

下列每項在當前 codebase 都**沒有**對應入口,刻意保持:

- **N2** persistence(snapshot 重啟丟失)、auth / TLS(明文 gRPC)
- **N3** L3 book reconstruction(`Snapshot::put` 整份覆寫,絕不合併)
- **N4** HA / failover / multi-region(單一 process / 單一監聽 endpoint)
- 自動 snapshot-on-subscribe(client 自己先 GetSnapshot 對齊,語意更乾淨)

## 8. 限制與已知 known issues

### 8.1 `senders` entry 不縮(B3,已固化為測試錨點)

`Bus::subscribe` 用 `entry().or_insert_with` 建立 broadcast::Sender。所有訂閱者
drop 後 entry 仍留在 DashMap 裡,佔用一個 `broadcast::Sender` 的 slot。當前
測試 `senders_entry_persists_after_all_subscribers_dropped` 固化此行為,作為未來
加 GC 改造時的**回歸告警點**(若未來改成 sender_count==0 時刪 entry,該測試
fail 即明確提示行為變更)。

**為何不修**:① 1k FIGI 規模下記憶體佔用 < 1MB;② 修需要 epoch 機制或重設計 entry
管理,複雜度與三天 deliverable 不匹配;③ 真實負載下 FIGI 集合是靜態的,entry
數量收斂。

### 8.2 wire 層 slow consumer 測試環境依賴(`#[ignore]`)

`grpc_slow_consumer_isolation_e2e` 改 `#[ignore]` 重定位為手動壓力測試。理由:
HTTP/2 stream flow control window + adaptive window + TCP buffer 是
**deployment-level tuning**,不是 logic-level invariant。試圖 tune 壓力參數讓
e2e 在 macOS M-series + adaptive window 上必爆,既不可靠又不解決真正的問題。

**I2 本身已由 bus.rs unit 層的兩個 deterministic 測試守住**
(`slow_consumer_isolation` 慢 + `disconnected_subscriber_does_not_stall_others`
斷)——那兩個與 buffer 大小無關。e2e 保留代碼 + `#[ignore]` 的價值在:
① reviewer 按「slow consumer」搜尋仍命中;② 手動跨主機 / Linux 環境驗證 wire
容量假設;③ 檔頭量化推導表(buffer 4 層 + wire size 影響)是設計取捨素材。

### 8.3 `from_env` 全路徑未測

`ServiceConfig::from_env` / `UpstreamConfig::from_env` 各 env var 的解析、錯誤
路徑(`MDS_LISTEN` parse fail、`SIM_PACING` 大小寫)沒有自動化測試。原因:env
var 是 process-global state,並發測試互相干擾;`std::env::set_var` 在 Rust
2024 edition 已 `unsafe`。改造方向:抽 `parse_env<T>` 泛型內部函式獨立測試,
或加 `serial_test` crate——本次跳過。

### 8.4 `client.rs` 錯誤路徑 / 網路中斷

`bin/client.rs` 是 README §6 要求的 demo binary,不在 crate library 責任內。
reviewer 跑 `cargo run --bin client` 手動驗證連線、stream 中斷等行為;
client.rs 文件 doc 列「預期輸出」段作為驗收錨點。
